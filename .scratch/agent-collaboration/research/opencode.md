# OpenCode integration evidence: visible session control

**Scope and method.** This is planning evidence only, checked **2026-09-09** against OpenCode's official documentation and the official `anomalyco/opencode` `dev` source tree. It does not run OpenCode, alter configuration, or select an adapter. The public SDK/docs describe the stable-facing API; the source observations identify current implementation details and experimental surfaces that require version pinning and runtime validation.

## Verified architecture and same-live-session evidence

OpenCode documents a client/server architecture: running `opencode` starts both a TUI and a server, and the TUI is a client talking to that server. The server supports multiple clients; `opencode serve` instead starts a standalone headless server. Crucially, the **Server -> How it works** and **Connect to an existing server** sections state that an existing TUI can be connected to through its server, and that `/tui` can drive the TUI (including prefill/run prompt), which OpenCode IDE plugins use. [Server docs, headings “How it works”, “Connect to an existing server”](https://opencode.ai/docs/server/#how-it-works).

Official source corroborates this rather than merely implying it. `packages/opencode/src/cli/cmd/attach.ts` implements `opencode attach <url> --session <id>` by validating the remote session then running the TUI against that URL. `packages/opencode/src/cli/cmd/tui.ts` similarly runs the ordinary TUI through a server transport; with explicit networking it obtains a server URL and authenticating headers. Therefore, **verified fact:** a visible TUI can attach to a running server and select a supplied server-side session ID. [Source: `attach.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/cli/cmd/attach.ts), [Source: `tui.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/cli/cmd/tui.ts).

**Interpretation:** API automation that uses that *same server*, directory/workspace scope, and `sessionID` addresses the same persisted/live session state displayed by the attached TUI, rather than a separate CLI process. This is strongly supported by the shared session routes and the attached TUI's shared server transport. It is not a documented transactional concurrency guarantee: no source found specifies ordering or conflict handling when a human and automation both submit prompts or reply to a pending request at the same instant. Serialize writers in a future design.

## Supported control and observation surfaces

The supported starting point is `opencode serve` (default `127.0.0.1:4096`) or the JS/TS SDK. `createOpencode()` launches a new headless server and client; it does **not** attach to an already visible TUI. For an existing instance, use `createOpencodeClient({ baseUrl })`. The generated SDK covers all server APIs and the server publishes its exact OpenAPI 3.1 contract at `http://host:port/doc`; that runtime contract should be the compatibility authority. [SDK docs, headings “Create client”, “Client only”, “APIs”](https://opencode.ai/docs/sdk/#create-client); [Server docs, heading “Spec”](https://opencode.ai/docs/server/#spec); [SDK source: `server.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/server.ts).

For lifecycle control, documented session routes create/list/get/update/delete sessions, expose `/session/status`, send prompts either synchronously (`/message`) or asynchronously (`/prompt_async`), and abort a running session through `POST /session/:id/abort`. Message list/get return message information and parts. The SDK names these `session.create`, `session.status` (server table), `session.prompt`, `session.messages`, `session.message`, and `session.abort`. A synchronous prompt waits for response; async prompt returns 204 and must be paired with event/status/message observation. This covers **start, prompt, observe, interrupt, and collect result** without terminal keystroke automation. [Server docs, headings “Sessions”, “Messages”](https://opencode.ai/docs/server/#sessions); [SDK docs, heading “Sessions”](https://opencode.ai/docs/sdk/#sessions).

For live observation, subscribe to server-sent events: `GET /event` (instance stream) or `/global/event` (global stream), with `client.event.subscribe()` returning an async stream. The current server source sends `server.connected`, emits matching events by instance directory/workspace, sends a ten-second `server.heartbeat`, and ends on `server.instance.disposed`. These are observed implementation behavior; event type/payload schemas must be read from the running `/doc` API and SDK types rather than hard-coded from this note. [SDK docs, heading “Events”](https://opencode.ai/docs/sdk/#events); [Server docs, heading “Global”](https://opencode.ai/docs/server/#global); [Source: `handlers/event.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts).

Plugins are a second observation/customization mechanism, not a replacement remote-control transport. Official docs say plugin functions receive an SDK `client` and may subscribe through an `event` hook. Listed events include `session.created`, `session.status`, `session.idle`, `session.error`, `message.updated`, `message.part.updated`, `permission.asked/replied`, and TUI events. `session.idle` is the documented completion signal example. Plugins load from project/global directories or config npm packages, run in stated load order, and their hooks run sequentially. [Plugins docs, headings “Use a plugin”, “Events”, “Send notifications”](https://opencode.ai/docs/plugins/#events).

## Correlation, results, and human decisions

The durable primary correlation key is `session.id`. Each message is retrieved under that session and has `messageID`; message contents are represented as `parts`, which supply part-level correlation for streamed/tool output. Prompt bodies may provide a `messageID`, and result APIs return `{ info: Message, parts: Part[] }`. There is no separately documented “turn ID”; a planning implementation should treat one submitted user message and the resulting assistant message/parts as a turn, record server-generated IDs, and correlate event payloads only after inspecting their typed schema for the installed version. [Server docs, headings “Sessions”, “Messages”](https://opencode.ai/docs/server/#sessions); [SDK docs, heading “Types”](https://opencode.ai/docs/sdk/#types).

Human approval can remain server-mediated. Permission configuration supports `allow`, `ask`, and `deny`; “ask” presents once/always/reject in the UI, while “always” lasts for the current OpenCode session. The documented legacy session permission route is `POST /session/:id/permissions/:permissionID` with `{ response, remember? }`. Current official source also exposes `GET /permission` and `POST /permission/:requestID/reply`, explicitly listing/replying to pending requests across sessions. Similarly, current source exposes `GET /question`, `POST /question/:requestID/reply`, and `/reject`. Thus a controller can **surface and route** pending approvals/questions to a human TUI/UI, but it must not silently call reply/approval endpoints if human takeover is required. [Permissions docs, headings “Configuration”, “What ‘Ask’ Does”](https://opencode.ai/docs/permissions/#what-ask-does); [Server docs, heading “Sessions”](https://opencode.ai/docs/server/#sessions); [Source: `groups/permission.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/groups/permission.ts); [Source: `groups/question.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/groups/question.ts).

TUI-specific SDK endpoints (`appendPrompt`, `submitPrompt`, `clearPrompt`, session/model/help dialogs, toast) can visibly stage or invoke actions in a connected TUI. Current source labels the TUI HttpApi group “Experimental”; its handlers publish TUI events, while `selectSession` validates the `ses...` ID then publishes selection. This gives concrete visibility/takeover mechanics, but it does not prove every remote TUI control endpoint has stable semantics or that a headless server has an active TUI consumer. Treat success boolean as command accepted/published, not proof that a person saw it. [SDK docs, heading “TUI”](https://opencode.ai/docs/sdk/#tui); [Source: `groups/tui.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/groups/tui.ts); [Source: `handlers/tui.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/handlers/tui.ts).

## Authentication, configuration, versions, and platform constraints

`OPENCODE_SERVER_PASSWORD` enables HTTP Basic authentication; username defaults to `opencode` and can be changed by `OPENCODE_SERVER_USERNAME`. `opencode attach` has matching `--password`/`--username` options. A server without the password is unsecured (the current `serve.ts` warns). Bind defaults to loopback; exposing a hostname, mDNS, or permissive CORS expands attack surface. [Server docs, headings “Usage”, “Authentication”](https://opencode.ai/docs/server/#authentication); [Source: `serve.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/cli/cmd/serve.ts); [Source: `attach.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/cli/cmd/attach.ts).

Configuration is merged by precedence and can materially change models, providers, permissions, plugins, server address, or managed policies. Relevant layers include global/project configs, `OPENCODE_CONFIG`, `OPENCODE_CONFIG_CONTENT`, and highest-priority managed macOS/Linux/Windows settings. The server is project/workspace scoped: SDK client source adds `x-opencode-directory` and rewrites it to the directory query for reads; server event filtering also keys on directory/workspace. A future integration must explicitly preserve directory/workspace context, not assume a base URL identifies one project. [Config docs, headings “Precedence order”, “Server”](https://opencode.ai/docs/config/#precedence-order); [SDK source: `client.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/client.ts); [Source: `handlers/event.ts`](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/server/routes/instance/httpapi/handlers/event.ts).

As checked, the latest GitHub release is **v1.18.30**, published **2026-09-09T03:34:27Z**, and `@opencode-ai/sdk` `dev` package declares `1.18.30`. The official README supports macOS (Apple Silicon/Intel), Windows x64, and Linux desktop downloads, while CLI package-manager install choices vary by OS. Current source contains experimental API groups and legacy shims, so require a tested version range, runtime health/version check, and OpenAPI/schema feature detection. [Official release API](https://api.github.com/repos/anomalyco/opencode/releases/latest); [SDK package source](https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/package.json); [Official README, headings “Installation”, “Desktop App (BETA)”](https://github.com/anomalyco/opencode/blob/dev/README.md).

## Open questions to validate before implementation

1. No official contract located that defines concurrent prompt submission, abort-versus-submit ordering, multi-client ownership/locking, or exactly-once event delivery/replay. SSE reconnection needs state reconciliation using session status and message list.
2. No official guarantee located that `/tui` commands target one particular attached TUI when multiple TUIs share a server, or that a boolean response means presentation/interaction occurred. Verify against the exact deployed version with two clients.
3. The public server docs list legacy session-permission route whereas current source additionally has global pending permission/question routes and marks some HttpApi groups experimental. Inspect `/doc` and SDK generated methods at integration time.
4. “Visible TUI address same session” is verified for `attach --session` and shared server state; actual terminal-pane ownership, focus, and input multiplexing are outside OpenCode's HTTP contract and remain a host terminal concern.
